## 八、系统架构目标与选型

### 8.1 项目名称
JC RAG 智能知识库系统

### 8.2 核心目标
构建一套支持离线部署、双设备兼容、可无缝切换本地/在线大模型的 JC RAG 智能问答系统，服务于知识管理、检索问答、决策辅助、培训教学等场景。

### 8.3 核心约束
- 开发机与内网生产机均为 Windows
- 内网生产机无外网权限，必须纯离线运行
- 大模型支持在线 API 与本地 Ollama 双模式切换
- 嵌入模型全程本地调用
- 前后端分离
- SpringBoot 统一做权限、审计、配置、接口聚合
- Python 仅负责文档处理、向量化、检索、模型调用、Agent/Skill 编排
- 拷贝项目目录 + Ollama 模型目录即可部署

### 8.4 总体技术选型

| 层级 | 技术 | 作用 | 选型理由 |
|---|---|---|---|
| 前端层 | Vue3 + TypeScript + Vite + Element Plus | 对话、知识库管理、系统设置、用户权限界面 | 轻量、组件成熟、适合后台系统 |
| API后端 | Spring Boot 3.x + Java 17 | 用户权限、系统配置、文件管理、日志审计、服务监控 | 适合企业级后台和 RBAC |
| 安全认证 | Spring Security + JWT + Redis | 登录认证、权限校验、会话控制 | 成熟、稳定、可审计 |
| RAG服务层 | Python 3.10/3.11 + FastAPI | 文档解析、向量化、检索、问答、Agent/Skill | 与 LangChain 和模型生态兼容最好 |
| RAG编排 | LangChain | 文档切分、召回、提示词编排、工具调用 | 便于快速实现可控 RAG |
| 嵌入模型 | bge-large-zh-v1.5 | 文本向量化 | 已本地具备，中文语义效果好 |
| 向量检索 | Elasticsearch 8.x | 向量存储、语义检索、元数据过滤 | 已部署，可统一检索能力 |
| 本地 LLM | Ollama | 本地离线模型运行 | 便于切换模型，适合复制部署 |
| 在线 LLM | OpenAI兼容 API / 自定义 HTTP API | 在线大模型接入 | 与本地模型统一抽象 |
| 文件存储 | MinIO | 文档对象存储、下载、预览 | 已部署，适合文档管理 |
| 关系数据库 | MySQL 8.0 | 用户、权限、配置、日志、文档元数据 | 结构化数据管理稳定 |
| 缓存/会话 | Redis 7 | 会话、验证码、限流、缓存 | 性能高、集成方便 |
| 部署编排 | docker-compose | 管理基础中间件 | 简化部署 |

## 十、模块间交互流程

### 10.1 文档上传入库流程
```text
前端上传文件
  -> SpringBoot 做权限校验
  -> 文件写入 MinIO
  -> 元数据写入 MySQL
  -> SpringBoot 调用 Python RAG 服务
  -> Python 执行解析、清洗、切块、向量化
  -> 写入 Elasticsearch 索引
  -> 回写处理结果
  -> SpringBoot 更新文档状态与日志
  -> 前端显示处理状态
```

Python RAG 服务的解析流水线（`POST /knowledge/parse`）实现了以下性能优化：
- 启动时 `warmup_embedding()` 预加载 bge-large-zh-v1.5（1.3GB），避免首请求 5-15s 冷启动延迟
- PDF 多进程并行解析：每 30 页一组，进程数 = min(cpu_count-1, 8)
- OCR 触发判断基于「字符密度 + 是否含图像」（`should_ocr_pdf_page`），同时兼容扫描件与文字页，避免对正常 PDF 误触发 OCR
- batch_size 按设备类型推荐：CUDA 独显 256 / Intel XPU 与 DirectML 集显 128 / Apple MPS 128 / CPU 64 / LM Studio 与 Ollama API 32
- CUDA 设备根据 `mem_get_info` 实时显存动态收缩 batch_size，避免 OOM
- CPU 设备启动时主动设置 `torch.set_num_threads` 榨满多核
- embedding 与 ES bulk 写入并发：用 ThreadPoolExecutor 异步提交 ES 写入任务，GPU 不等 ES
- 每阶段独立计时并写入日志 `[perf]`，便于定位瓶颈：`download / extract / split / embed / es_wait`
- 响应体返回 `perf` 字段（含每阶段耗时、batch_size、设备名、OCR 命中页数），供前端展示

#### 10.1.x Embedding 设备选择策略

`GET /system/devices` 探测本机可用 Embedding 设备，按性能由高到低排序：
1. 独显 GPU（NVIDIA CUDA / Intel Arc A 系列 / AMD Radeon RX 等）
2. 集显 GPU（Intel Iris Xe / UHD / Intel Arc Graphics / AMD Radeon Graphics 等）
3. Apple Silicon GPU（MPS）
4. LM Studio 本地 GGUF API
5. Ollama Embedding API（自动枚举 tags 中含 `embed/bge/e5/gte/nomic` 关键字的模型）
6. CPU

设备名按命名规则识别独显/集显：
- CUDA 后端默认独显（笔记本核显不走 CUDA）
- `Intel Arc Graphics`（无 A/B 型号后缀）视为集显，对应 Meteor Lake/Lunar Lake/Arrow Lake 核显
- `Intel Arc A380/A580/A750/A770/B580 ...` 等含型号后缀的视为独显
- 名字含 `Iris Xe / UHD / AMD Radeon Graphics` 等关键字视为集显

前端设备下拉框（系统设置 → 参数配置 → Embedding 设备）支持：
- 显示所有可用设备的友好名称，超长名称悬停 tooltip 完整展示
- 浏览按钮（嵌入 Embedding 模型路径文本框）默认隐藏，悬停或聚焦文本框时显示
- 选择 LM Studio 时显示其 baseUrl 输入框
- 刷新按钮重新枚举设备
- `Auto` 选项由后端 `_resolve_best_device` 在保存时按上述优先级解析为具体设备 ID

### 10.2 问答流程
```text
用户提问
  -> 前端调用 SpringBoot 会话接口
  -> SpringBoot 鉴权并记录会话
  -> 转发到 Python RAG 服务
  -> Python 执行问题改写、上下文拼接、向量检索
  -> 召回 TopN 文档块
  -> 构建 Prompt
  -> 调用在线模型或离线 Ollama
  -> 流式返回答案 + 引用来源
  -> SpringBoot 落库日志和消息
  -> 前端流式展示
```

### 10.3 模型切换流程
```text
前端系统设置修改模型模式
  -> SpringBoot 保存配置到 MySQL
  -> SpringBoot 通知 Python 刷新配置
  -> 后续请求按新模式路由
  -> 不需要改业务代码
```

## 十一、在线 / 离线模型双模式方案

### 11.1 统一抽象
Python 侧定义统一模型适配接口：
- `generate()`
- `stream_generate()`
- `health_check()`
- `list_models()`

实现两个 Provider：
- `OnlineApiProvider`
- `OllamaProvider`

### 11.2 离线模型接入
- 本地 Ollama 地址固定支持配置，默认：`http://localhost:11434`
- 对话接口：`http://localhost:11434/api/chat`
- 模型列表接口：`http://localhost:11434/api/tags`
- 前端系统设置页面支持：
  - 模式切换：在线 / 离线
  - 离线模型下拉选择
  - 温度、`top_p`、`max_tokens` 参数配置
  - Ollama 地址配置

### 11.3 在线模型接入
- 支持 OpenAI 兼容 API
- 支持配置：`base_url` / `api_key` / `model_name` / `temperature` / `top_p` / `max_tokens`

### 11.4 切换原则
- 所有切换只改配置，不改代码
- SpringBoot 作为配置中心唯一写入口
- Python RAG 服务通过配置拉取或刷新接口更新运行态

## 十二、Agents 与 Skills 方案

### 12.1 结论
支持，但作为可插拔增强模块实现，首版默认受控启用。

### 12.2 Agent 定位
Agent 用于复杂任务：
- 制定方案
- 对比多种方案
- 生成文书草稿
- 案例复盘分析

### 12.3 Agent 可调用工具
- `rag_search`
- `doc_lookup`
- `answer_generate`
- `template_render`
- `plan_compare`
- `terminology_explain`
- `session_memory`

### 12.4 Skill 类型
- 基础技能：文档检索、问题解析、回答生成、术语解释、条款定位
- 行业场景技能：方案生成、计划制定、案例分析、条令解读、文书生成、推演复盘

### 12.5 集成原则
- 先检索，后生成
- 所有 Skill 尽量返回引用来源
- Agent 只能调用白名单工具
- 所有执行步骤必须可追溯、可中断

### 16.1 初始化脚本组织方式
为减少部署复杂度，数据库与索引脚本采用"同类合并"的方式维护：
- MySQL 总脚本：`docs/sql/mysql/001_jc_rag_all_in_one.sql`
- Elasticsearch 总脚本：`docs/es/001_jc_rag_all_in_one.http`

说明：
- MySQL 总脚本中包含全部核心表、基础数据、模型配置、Agent/Skill 初始化数据
- Elasticsearch 总脚本中包含主向量索引和可选会话记忆索引
- 后续如有结构升级，新增增量升级脚本，不再拆成多个初始化碎片文件

## 十九、关键设计决策

- SpringBoot 统一做权限、配置与审计，前端不直连 Python/ES/MinIO
- Python 仅承担 RAG 和模型能力，降低耦合
- Agent 为增强模块，不替代主问答链路
- Elasticsearch 统一承担向量与过滤检索，避免引入额外向量数据库
