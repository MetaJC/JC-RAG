# 测试文档总览（用例库 + 测试 Agent）

> 测试用例库 + 测试工程师 Agent 的统一入口。覆盖：工作流、目录结构、命名规约、Agent 协议、CI 接入。

## 一、4 类角色，4 件事

| 角色 | 主要操作 | 用到的文档 |
|------|----------|------------|
| **开发者** | 开发完功能 → 写测试用例 | 本文档 §四, [_template/feature.md](_template/feature.md) |
| **测试 Agent** | 自动/手动执行用例 | 本文档 §五（Agent 协议） |

| **CI / DevOps** | 接入 GitLab CI / GitHub Actions | 本文档 §六 |

## 二、工作流（4 步）

```
[开发完功能]
    ↓
[1. 写测试用例] → docs/test/features/{FEATURE_ID}/test-cases.md   (开发者)
    ↓ git push
[2. CI 钩子触发] → POST /api/test/run?feature={FEATURE_ID}        (CI / GitLab CI)
    ↓
[3. Agent 自动跑] → 调 AutoCheck / 模拟操作 / 验证 Expected
    ↓
[4. 写结果] → docs/test/features/{FEATURE_ID}/result-{YYYYMMDD-HHmm}.md
```

**手动触发**（3 种，等效）：
- **Agent 对话**：在 jc-rag-user-web "测试工程师" 智能体中输入 `测试 MEM-L0` 或 `测试 TC-MEM-L0-001`
- **CLI**：`python jc-rag-service/scripts/test_agent.py --feature MEM-L0`
- **REST**：`POST /api/test/run` `{ "feature": "MEM-L0", "caseId": "TC-MEM-L0-001" }`

## 三、目录结构与命名规约

### 3.1 目录结构

```
docs/test/
├── README.md                   ← 本文件（总览）
├── _template/
│   ├── case.md                 ← 单条用例模板（Agent 解析用）
│   └── feature.md              ← 功能级用例集模板（开发者用）
├── features/                   ← 按功能组织（跟开发 1:1 对应）
│   ├── AUTH-LOGIN/
│   │   ├── test-cases.md       （开发者写）
│   │   └── result-20260703-1530.md  （Agent 写）
│   ├── MEM-L0/                 （示例：L0 短期记忆）
│   │   ├── test-cases.md
│   │   └── result-*.md
│   ├── MEM-L1/
│   ├── MEM-L2/
│   ├── MEM-L3/
│   ├── MEM-P01-FORGET/         (P0-1 GDPR)
│   ├── CHAT-SEND/              (聊天)
│   ├── KB-UPLOAD/              (知识库)
│   ├── ...
└── data/                       ← 测试账号 / 测试数据
    ├── users.md
    └── knowledge-bases.md
```

### 3.2 功能 ID（FEATURE_ID）格式

格式：`{MODULE}-{NAME}`，大写连字符。

| 模块 | 缩写 | 说明 |
|------|------|------|
| 认证授权 | AUTH | 登录/注册/找回/滑块 |
| RBAC | RBAC | 用户/角色/权限/菜单/数据权限 |
| 知识库 | KB | 增删改查/导入/解析/检索/授权 |
| 聊天 | CHAT | 会话/消息/SSE 流式/多模态 |
| 记忆 | MEM | L0/L1/L2/L3 + P0-1/2/3 |
| 偏好 | PREF | 5 项 OK + 记忆文件 + 被遗忘权 |
| 管理后台 | ADMIN | 仪表盘/审计/日志 |
| 商业版 | PRO | KB 商业增强/高级搜索/评测 |
| 跨切面 | CROSS | 性能/安全/合规/SEO |

示例：`MEM-L0`、`AUTH-LOGIN`、`KB-UPLOAD`、`MEM-P01-FORGET`（P0-1 一键忘记我）

### 3.3 用例 ID 格式

格式：`TC-{FEATURE_ID}-{NNN}`（NNN 三位数字，同 feature 内从 001 起）。
示例：`TC-MEM-L0-001`、`TC-AUTH-LOGIN-003`、`TC-MEM-P01-FORGET-002`

### 3.4 测试粒度（4 档）

| 粒度 | 调用 | 用途 | 耗时 |
|------|------|------|------|
| 全局 | `--feature GLOBAL-SMOKE` 或对话 "跑冒烟" | CI 每次 push | 10 min |
| 模块 | `--feature MEM`（拉所有 MEM-*） | 大版本发布前 | 1-2 h |
| 功能 | `--feature MEM-L0` | PR 必跑 | 10-30 min |
| 单条 | `--case TC-MEM-L0-001` | 开发期调试 | 1-5 min |

## 四、开发者流程（主流程）

### Step 1: 完成功能开发

```bash
git checkout -b feature/MEM-L0
# ... 写代码 ...
git commit -m "feat(memory): 实现 L0 短期记忆"
```

### Step 2: 写测试用例

复制功能模板：
```bash
cp docs/test/_template/feature.md docs/test/features/MEM-L0/test-cases.md
```

填写内容（参考 [features/MEM-L0/test-cases.md](features/MEM-L0/test-cases.md)）：
- 顶部 `Feature:` 块：填 ID / Name / Module / CodeRefs
- 10 条 `## TC-MEM-L0-NNN` 用例，每条 8 个必填字段
- AutoCheck YAML 可选（Agent 跑得靠它）

### Step 3: 本地手动验证

用 Python CLI 跑一遍：
```bash
# 一次性安装（本轮交付时 agent.py 还没实现，先用 mock）
python jc-rag-service/scripts/test_agent.py --feature MEM-L0

# 输出：
# [测试工程师] 收到: 测试 MEM-L0
#   ┌─ TC-MEM-L0-001 ✅ pass (1234ms)
#   ├─ TC-MEM-L0-002 ✅ pass (890ms)
#   ├─ TC-MEM-L0-003 ❌ fail (567ms)
#   └─ ...
#   统计: 8 pass / 2 fail
# 详见: docs/test/features/MEM-L0/result-20260703-1530.md
```

### Step 4: 提交并推送
```bash
git add docs/test/features/MEM-L0/test-cases.md
git commit -m "test(memory): MEM-L0 完整测试用例 (10 条)"
git push origin feature/MEM-L0
```

### Step 5: 触发 CI 自动测试

push 后，GitLab CI 自动：
1. 检测变更文件，匹配到 `docs/test/features/MEM-L0/`
2. 调 `POST /api/test/run { "feature": "MEM-L0", "trigger": "ci" }`
3. Agent 跑 10 条用例
4. 写 `result-{TIMESTAMP}.md`
5. 失败则 PR 标红，阻塞 merge

### 4.1 PR 模板

```markdown

(简述)

## 关联测试用例
```

## 五、测试工程师 Agent 协议

### 5.1 角色定义

你是 **JC RAG 平台的测试工程师**，职责：
- 接收测试指令（单条 / 功能 / 模块 / 全局）
- 从 `docs/test/features/{FEATURE_ID}/test-cases.md` 读取用例
- 按 `PreConditions` 准备环境（登录 / 启动服务 / 准备数据）
- 按 `Steps` 顺序执行（调 API / 模拟 UI 操作 / 查 DB / 查 ES / 查文件）
- 按 `Expected` 验证结果
- 按 `AutoCheck` 跑机读断言
- 输出结果到 `result-{YYYYMMDD-HHmm}.md`
- 返回 PASS / FAIL 简报

原则：
- **零信任**：不假设任何前置条件已就绪，每次执行前主动 setup
- **隔离性**：测试数据用 `test_user_*` 前缀，不污染生产数据
- **可重入**：同一用例跑两次结果应一致
- **快速失败**：第一步失败立即停止，不浪费时间
- **可观测**：所有 API 调用 / DB 查询 / 断言记录到 result，便于 debug

### 5.2 工具集（Tool Schemas）

| 工具 | 用途 |
|---|---|
| `read_file` | 读文件 |
| `api_call` | 调 REST API（method / url / headers / body / timeout） |
| `sse_listen` | SSE 流监听（on_event / timeout） |
| `db_query` | MySQL 查询（sql / params / limit） |
| `es_query` | ES 查询（index / body） |
| `file_check` | 文件系统（path / exists / content_contains / size_greater_than） |
| `playwright` | 浏览器自动化（action / selector / value） |
| `write_result` | 写结果（feature_id / results / output 路径） |

> E2E 用例默认用 API 模拟（快 / 稳），仅当用例必须验证 UI 时才用 playwright。

### 5.3 输入协议

| 指令 | 含义 | 示例 |
|------|------|------|
| `测试 {FEATURE_ID}` | 跑一个功能所有用例 | `测试 MEM-L0` |
| `测试 {FEATURE_ID} {NNN}` | 跑一个功能的某条用例 | `测试 MEM-L0 001` |
| `测试 TC-{...}-{NNN}` | 直接用用例 ID | `测试 TC-MEM-L0-001` |
| `测试模块 {MODULE}` | 跑一个模块所有功能 | `测试模块 MEM`（跑 MEM-* 所有） |
| `跑冒烟` | 全局冒烟 | （待写） |
| `重跑 {FEATURE_ID}` | 重跑最近 result 失败的用例 | `重跑 MEM-L0` |

自然语言（LLM 解析）：
- "帮我测一下 L0 短期记忆" → `测试 MEM-L0`
- "L0 那 5 条用例跑一下" → `测试 MEM-L0`（拿 5 条）
- "TC-MEM-L0-001 这条" → `测试 TC-MEM-L0-001`
- "记忆模块全跑" → `测试模块 MEM`

### 5.4 输出协议

#### Chat 实时输出（对话时）
```
[测试工程师] 收到: 测试 MEM-L0
  读取 docs/test/features/MEM-L0/test-cases.md ... 10 条用例
  ┌─ TC-MEM-L0-001 多轮对话上下文 ─── PASS (1234ms)
  ├─ TC-MEM-L0-002 10 轮后丢弃 ────── PASS (890ms)
  ├─ TC-MEM-L0-003 Token 预算截断 ──── FAIL (567ms)
  │   期望: history.length <= 4000 tokens
  │   实际: history.length = 5234 tokens
  │   详见: docs/test/features/MEM-L0/result-20260703-1530.md
  └─ ...
  统计: 7 pass / 2 fail / 1 blocked / 耗时 12.3s
```

#### 落盘 result 文件
写到 `docs/test/features/{FEATURE_ID}/result-{YYYYMMDD-HHmm}.md`，包含：
- Summary（pass / fail / blocked 数 + TotalElapsedMs）
- 每条用例的 Status / ElapsedMs / Actual / Assertions / Error / StackTrace / Recommendation

### 5.5 REST API

| 方法 | 路径 | 用途 |
|------|------|------|
| POST | /api/test/run | 触发一次测试运行 |
| GET | /api/test/result/{featureId} | 查最近 result |
| GET | /api/test/result/{featureId}/history | 查历史 result 列表 |
| GET | /api/test/status | Agent 状态（在线/离线/当前任务） |

#### POST /api/test/run

**Request**:
```json
{
  "feature": "MEM-L0",
  "caseId": "TC-MEM-L0-001",   // 可选，不传跑整个 feature
  "trigger": "ci"               // ci | manual
}
```

**Response**:
```json
{
  "runId": "run-20260703-1530-MEM-L0",
  "status": "running",          // running | pass | fail | error
  "feature": "MEM-L0",
  "totalCases": 10,
  "passCount": 0,
  "failCount": 0,
  "resultPath": "docs/test/features/MEM-L0/result-20260703-1530.md"
}
```

### 5.6 错误处理

| 错误 | 行为 |
|---|---|
| `test-cases.md` 不存在 | 返回 404，"未找到用例，请先写测试用例" |
| `AutoCheck` YAML 解析失败 | 标记 `blocked`，提示开发者修正 |
| 后端服务未启动 | 标记 `blocked`，提示"请先启动 jc-rag-user (8082) / jc-rag-service (8001)" |
| DB / ES 连接失败 | 标记 `blocked`，提示检查 MySQL / ES |
| 用例内部 assert 失败 | 标记 `fail`，记录实际值 + 期望值 + 堆栈 |
| Agent 自身异常（LLM 限流） | 重试 3 次，仍失败则 `error` |

## 六、CI 集成（DevOps 教程）

### 6.1 GitLab CI 示例（.gitlab-ci.yml）

```yaml
stages:
  - test

agent-test:
  stage: test
  image: python:3.11
  before_script:
    - pip install -r jc-rag-service/requirements-test.txt
  script:
    # 1. 检测受影响的 feature
    - python scripts/detect_changed_features.py > changed_features.txt
    # 2. 启动 jc-rag-user / jc-rag-service（用 docker compose）
    - docker compose up -d jc-rag-user jc-rag-service
    - sleep 30
    # 3. 跑 Agent
    - |
      while read feature; do
        python jc-rag-service/scripts/test_agent.py --feature "$feature" --auto || exit 1
      done < changed_features.txt
  artifacts:
    paths:
      - docs/test/features/*/result-*.md
    reports:
      junit: test-results.xml
  only:
    - merge_requests
    - main
```

### 6.2 detect_changed_features.py 思路

```python
import subprocess
changed = subprocess.check_output(['git', 'diff', '--name-only', 'origin/main...HEAD'], text=True)
features = set()
for path in changed.splitlines():
    if path.startswith('jc-rag-backend/') or path.startswith('jc-rag-frontend/'):
        # 从 git log 找关联的 FEATURE_ID (commit msg 约定 "feat(MEM-L0): ...")
        commit = subprocess.check_output(['git', 'log', '--oneline', '--', path], text=True)
        for line in commit.splitlines():
            if 'MEM-L0' in line: features.add('MEM-L0')
            if 'AUTH-LOGIN' in line: features.add('AUTH-LOGIN')
print('\n'.join(features))
```

## 七、Reviewer / PM 教程

### 7.1 看 PR 的测试状态

PR 页面会显示：
- `影响功能: MEM-L0`
- `本地 Agent: ✅ 8/10 pass`
- `CI 状态: ⏳ running`
- `result: docs/test/features/MEM-L0/result-20260703-1530.md`

### 7.2 读 result 文件
打开 `result-{TIMESTAMP}.md`：
```markdown
# Test Result: MEM-L0
- Summary: 7 pass / 2 fail / 1 blocked
...
## TC-MEM-L0-003 Token 预算截断
- **Status**: ❌ fail
- **Actual**: history.length = 5234 tokens (期望 <= 4000)
- **Recommendation**: 检查 L0 token 预算计算逻辑
```

### 7.3 决策

| 状态 | 决策 |
|---|---|
| 全 pass | ✅ 批准 merge |
| 部分 fail | ⚠️ 看 fail 是否阻塞主流程；不阻塞可批准，阻塞则打回 |
| blocked | ❌ Agent 环境问题，重跑或人工 |

## 八、常见问题（FAQ）

**Q1: 用例写完后多久生效？**
CI 钩子接 push 事件，push 后 5 分钟内自动跑。手动用 Agent 对话即时生效。

**Q2: 测试失败是开发问题还是用例问题？**
看 `result-*.md` 的 `Recommendation` 字段。fail 可能是代码 bug，也可能是用例期望太严格。

**Q3: 一次跑多个 feature 怎么写？**
暂无，需逐 feature 跑。或用 `--module MEM` 跑整个模块。

**Q4: Agent 跑挂了 / 假死？**
看 `result-*.md` 的 `StackTrace` 字段，或 Agent 日志（`/var/log/jc-rag/test-agent.log`，待配）。

**Q5: 用例数和功能数怎么对齐？**
`find docs/test/features -name 'test-cases.md' | wc -l` 应 = 已完成功能数（每周 review 一次）。

**Q6: L0 / L1 / L2 / L3 都能测吗？**
能，每个 feature 都有独立的 test-cases.md。但 L1/L2/L3 涉及异步任务，测试需要等待（建议 timeout 30s+）。
